# Developer-surface alignment

Use this map only when setup, public behavior, or contribution policy changes.
Update surfaces whose promise changed; do not perform a blanket rewrite.

| Surface             | Its single job                                                                | Verification                                            |
| ------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------- |
| Source TSDoc        | Exact class, method, option, parameter, return, and lifecycle contract        | TypeScript/lint and generated TypeDoc                   |
| `samples/`          | Focused executable capability pattern                                         | `npm run build` plus browser/device check as applicable |
| `templates/`        | Minimal copyable app setup                                                    | `npm run build` plus simulator smoke check              |
| `demos/`            | Composed showcase behavior                                                    | Relevant build and interaction smoke check              |
| `docs/docs/manual/` | Developer explanation, setup, limitations, permissions, and supported imports | `npm run build --prefix docs`                           |
| `README.md`         | Installation, first-use contract, dependency/security headline                | Root formatting and link/code review                    |
| `CONTEXT.md`        | Compact app-generation rules and canonical patterns                           | Verify every named API in the public entry              |
| `AGENTS.md`         | Repository architecture and contribution policy                               | Verify commands and paths against configuration         |
| `src/SKILL.md`      | In-tree SDK overview and public mental model                                  | Verify against `src/xrblocks.ts`, `Options`, and `Core` |
| `skills/xb-*`       | Task process and branch selection                                             | Validate the changed skill folder                       |

## Public-pattern rules

- Copy imports from the actual root or addon entry. For CDN apps, ensure the
  import map names every bare specifier used by that pattern and pins compatible
  peer versions.
- Use a sample/template path that the docs can link to; avoid a prose-only API
  example when executable code is warranted.
- State defaults, prerequisites, permissions, availability checks, cleanup, and
  simulator/device differences that change developer behavior.
- Keep unsupported or prototype status explicit. Do not promote an
  implementation beyond its tested transport/runtime surface.
- Add a manual page to `docs/sidebars.ts` only where the sidebar is explicit;
  manual pages otherwise use its autogenerated sidebar.

## Adding documentation when none exists

First decide whether the change needs explanation, a copyable runnable pattern,
or both:

- Use an existing `docs/docs/manual/` page when the feature extends a documented
  subsystem or changes setup, lifecycle, permissions, limitations, imports,
  options, or public API expectations for that subsystem.
- Add a new `docs/docs/manual/<Topic>.mdx` or `.md` page when the behavior is a
  new subsystem, addon, runtime mode, or cross-cutting concept that would make an
  existing page mix unrelated responsibilities.
- Add or update a `samples/` implementation plus a matching
  `docs/docs/samples/*.mdx` wrapper when developers need an executable pattern to
  copy, inspect, or smoke test. Prefer this over prose-only snippets for spatial
  behavior, browser permissions, simulator/device differences, AI calls, network
  flows, and XR interactions.
- Add or update a `templates/` implementation plus a matching
  `docs/docs/templates/*.mdx` page when the new pattern is a minimal app starting
  point rather than a focused feature demonstration.

For a new manual page, copy the local frontmatter style: set `title`, choose a
`sidebar_position` near adjacent subsystem pages, and write concise sections for
setup, imports, lifecycle or permissions, common usage, limitations, and links to
the executable sample/template. Because `docs/sidebars.ts` autogenerates the
manual sidebar from `docs/docs/manual`, most new manual pages do not need a
sidebar edit; only update explicit sidebars such as samples or templates when
adding a new item there.

Keep docs grounded in public code. Every documented symbol must be exported from
the root barrel or the relevant addon entry, every option must exist on
`Options`, and every example import must match the path that users can actually
load. If the feature is experimental, local-only, simulator-only, device-only,
or unsafe for production key handling, say that in the doc instead of burying it
in comments.

## Skill alignment

Workflow skills should tell agents how to compose a result. Legacy capability
skills can locate subsystem-specific examples and pitfalls, but their API claims
must be verified in code. When a public change invalidates an affected skill,
update or route that skill to the current workflow guide. Keep one authoritative
explanation for each behavior and use precise context pointers elsewhere.

## Documentation completion check

Search all developer surfaces for renamed/removed symbols and old import paths.
The documentation seam is closed only when the executable example builds, every
shown import resolves, every shown API is public, limitations match tested
behavior, and the docs build succeeds without broken links or MDX errors.
